# User Story and Acceptance Criteria

## User Story

A **User Story** is a short, high-level description of a feature or change written from the perspective of the user or customer. It explains who the user is, what they want to do, and why it matters, without prescribing how the solution should be built. A User Story helps the team stay focused on delivering value rather than implementation details. A User Story normally follows a format like **"As a [type of user], I want [a specific feature or functionality] so that [a specific benefit or outcome is achieved]."** In short: a User Story defines *the intent and outcome*.

### Example User Story

**As a** signed-in user on the Chocolatey Community Repository website,  
**I want to** have the ability to update my profile information  
**so that** my account details stay current.

## Acceptance Criteria

**Acceptance Criteria** define the specific conditions that must be met for a User Story to be considered complete and approved. They describe the expected behavior, rules, and constraints of the feature in a clear, testable way. Acceptance Criteria guide development, testing, and review by setting a shared understanding of what "correct" looks like. In short: Acceptance Criteria define *how we know the User Story is satisfied*.

### Example Acceptance Criteria

- [ ] The user can edit their name and email address.
- [ ] Required fields must be filled in before saving.
- [ ] Changes are saved successfully and persist after page refresh.
- [ ] The user sees a confirmation message after saving.
- [ ] Invalid input displays a clear error message.
- [ ] The user cannot save if validation errors exist.
- [ ] The user cannot edit another user’s profile.

## How the User Story and Acceptance Criteria Work Together

- The **User Story** describes what problem is being solved and for whom.
- **Acceptance Criteria** describe the conditions that prove the problem has been solved.
